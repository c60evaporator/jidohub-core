# jidohub-server


## 設計上のポイント

### API設計

#### APIの入出力は(0)のスキーマのシリアライズ形式にする
エンドポイントは predict(Sample) -> Output のHTTP写像とし、リクエスト/レスポンスのJSONスキーマを(0)から機械的に導出します。こうすると「nuscenes-viewer向けAPI」ではなく「adhubスキーマを話す汎用API」になり、どのクライアントからも同じ契約で使えます。画像や点群のような大きいバイナリはJSONに入れず、multipartまたはS3の署名付きURL参照にするのが実用的です。

#### 同期APIとジョブAPIの2面を持たせる
単発フレームの推論（Inferenceタブでの対話的な可視化）は同期でよいですが、シーン一括推論や自動アノテーションはジョブです。以前議論したジョブキュー + GPUワーカーの構成は、nuscenes-viewer側ではなくこの(6)の内部に置くのが正解です。これでnuscenes-viewerからCelery等の推論系依存が完全に消えます。

### モデル管理

#### モデルのライフサイクル管理（load/unload）を持たせる
GPUメモリは有限なので、「リポジトリID + revisionを指定してロード → コンテナ起動（docker runner）→ 推論受付 → アイドルでアンロード」という管理が(6)の固有責務になります。nuclioの関数デプロイに相当する部分です。

#### モデル一覧は3層に分解する
モデルの一覧管理は以下の3層に分解し、APIでもこれらの情報を提供する

1. モデルの正体（どんなモデルが存在するか）: agent_config.json を持つリポジトリそのもの。最終的には(1) Hubが正。(1)ができるまでの過渡期は、(6)が「登録済みモデルカタログ」（repo_id, revision, task, sensor_config, スキーマ、S3上の重みパス）を持つのが自然です。モデル登録のバリデーション（(0)のバリデータで形式検証、Dockerイメージビルド）も(6)の仕事にします。
2. デプロイ状態（今どのモデルが推論可能か）: ロード状況、GPU割当、ヘルス。これは純粋に(6)の責務です。
3. アプリ内の利用設定: 「自動アノテーションのデフォルトはこのモデル」「このシーンで実行した推論ジョブの履歴と結果」「Inferenceタブでの表示設定」。これはnuscenes-viewerの責務で、viewerのDBには repo_id + revision の参照と、シーン/サンプルに紐づくジョブ・推論結果だけを持たせます。

### Datasetをダウンロードして、複数モデルで性能評価した結果を記録する機能

推論ジョブが「モデル×サンプル列→出力の保存」なら、評価ジョブは「モデル×データセット→ハーネス実行→メトリクスの保存」であり、ジョブキュー、GPUワーカー、docker runner、カタログがそのまま流用できます。HuggingFaceで言えばOpen LLM Leaderboardの評価ジョブ基盤に相当し、adhub-webの将来機能（リーダーボード、モデルカードの実績値）への布石にもなります。その上で、設計を健全に保つためのポイントを4つ挙げます。

#### 1. jidohub-agentのハーネスとの関係: 「実行主体」と「オーケストレーター」

前回作った段階3のベンチマークハーネス（CLI）と今回のserver機能は競合しません。**serverの評価ジョブは、ワーカーコンテナ内でそのハーネスを呼び出すオーケストレーター**と位置づけてください。評価ロジック（データセットを回してpredictを呼び、devkit評価に渡す）はadhub-models側の一箇所に留め、serverは「どのモデル×どのデータセット×どの設定で実行するか」のスケジューリングと結果の記録だけを担います。ここを分けておかないと、ローカルCLIとserverで評価ロジックが二重実装され、数値がずれるという最悪の事態を招きます。ネイティブクラスもtrust_remote_codeモデルも、docker runner越しに同じ `predict(Sample)` 契約で叩けるので、ハーネス側はモデルの出自を意識する必要がありません。これがまさにこれまでの設計の配当です。

#### 2. スコープを「評価実験の管理」に限定する

「実験管理」という言葉には注意が必要です。MLflowやW&Bが担う本来の実験管理（学習中のメトリクス曲線、ハイパーパラメータ探索、アーティファクト管理）まで踏み込むと、それ自体が巨大なプロダクト領域で、既存ツールと競合して勝ち目がありません。ここで作るべきは**「評価ラン（evaluation run）のレジストリ」**、つまり

> 誰が・いつ・どのモデル（repo_id + revision）を・どのデータセット（id + version/split）で・どの評価設定で実行し・どんなメトリクスが出たか

の不変レコードの蓄積に限定することを勧めます。学習系の実験管理は将来もMLflow等に任せ、adhubは「確定した重みの標準化された評価」だけを引き受ける。この線引きなら、Trainerを初期スコープから外した判断とも整合します。

#### 3. 比較可能性の担保が価値の核心

「複数モデルの性能比較」が意味を持つのは、評価条件が固定されているときだけです。そこで評価ランのレコードには最低限、

- モデル側: `repo_id` + `revision`（コミット固定）
- データセット側: データセットID + **バージョン/スナップショット** + split（val等）
- 評価設定: 評価コードのバージョン（adhub-modelsのバージョン）、devkitバージョン、eval configのハッシュ
- 実行環境: GPU種別、Dockerイメージタグ

を必須で記録し、**UIやAPIでの「比較」は評価設定ハッシュが一致するラン同士に限定する**（不一致の比較は警告付きで許す）のが健全です。これはadhub-datasetsに「データセットのバージョニング」という要件を逆流させる点に注意してください。nuScenes valのような固定データセットは楽ですが、将来ユーザーがアップロードするデータセットを評価対象にするなら、リポジトリと同じくrevisionで固定できる必要があります。早めにスキーマへ入れておく価値があります。

#### 4. 結果の「正」の置き場所とbenchmark.jsonの関係

評価ランの記録はserverのDBが正で良いですが、前回「段階3の結果はモデルリポジトリの `benchmark.json` に書く」と決めた話との関係を整理しておく必要があります。両者は性質が違います。

- `benchmark.json`: モデル所有者が自己申告としてリポジトリに置く実績値（モデルカードの一部）
- serverの評価ラン: プラットフォームが統制された条件で実行した第三者検証的な記録

この2つを混ぜない（serverの結果を勝手にbenchmark.jsonへ書き戻さない）ことを勧めます。むしろ将来のadhub-webでは、モデルページに「self-reported」と「platform-verified」を並べて表示する形にすると、Verifiedバッジ構想とも噛み合い、リーダーボードの信頼性がプラットフォームの差別化要素になります。CenterPointネイティブ実装の検証で作る最初の評価ランが、そのままこの「platform-verified評価」第1号のドッグフーディングになる、という位置づけです。

まとめると、追加自体は適切で、設計上の要点は「評価ロジックはadhub-modelsに一元化しserverはオーケストレーションに徹する」「スコープは評価ランレジストリに限定」「revision・データセットバージョン・評価設定ハッシュで比較可能性を担保」「自己申告値とプラットフォーム検証値を区別」の4点です。
